common:header.adoc[]

In this guide, you will use Micronaut Data JDBC with Oracle transaction priority. A background transaction takes a row lock with `LOW` priority while a checkout transaction requests the same row with `HIGH` priority. Oracle can automatically roll back the lower-priority blocker, allowing the checkout to complete.

Micronaut Data applies the priority by setting the Oracle session when the transaction starts and restores the session when the transaction ends. Application code only declares the priority; it does not issue `ALTER SESSION` statements.

== Configure Oracle transaction priority

Transaction priority is an Oracle instance feature. The database administrator chooses how long a higher-priority transaction waits and whether Oracle rolls back the lower-priority transaction:

* `PRIORITY_TXNS_HIGH_WAIT_TARGET` controls how long a `HIGH` transaction waits for a lower-priority blocker.
* `PRIORITY_TXNS_MEDIUM_WAIT_TARGET` controls the equivalent wait for a `MEDIUM` transaction.
* `PRIORITY_TXNS_MODE=ROLLBACK` enables priority-based rollback.

For this guide, the Oracle Free Test Resources container copies a startup script into the database image:

resource:oracle/priority-txns.sql[]

<1> `copy-to-container` copies the SQL file before the Oracle container starts.
<2> The script first sets CDB defaults, then switches to `FREEPDB1`, the PDB used by the Oracle Test Resources provider, and applies the same values there.
<3> Oracle Free executes SQL files in `/container-entrypoint-startdb.d` through `sqlplus / as sysdba`, so the script can set instance parameters without granting the application user DBA privileges.
<4> `SCOPE=MEMORY` keeps the settings local to the throwaway container.

The startup script runs each time the database starts. If you change it while a Test Resources container is already running, run `./gradlew stopTestResourcesService` (and remove any manually started Oracle container) before retrying so the new script is applied.
The Oracle container log should include `CONTAINER: running /container-entrypoint-startdb.d/priority-txns.sql`.

== Priority-aware service

The service has one method for each priority:

source:AccountService[]

<1> `@OracleTransactional` is a transaction boundary that also applies the selected Oracle session priority.
<2> The low-priority method updates the row, signals that the lock is held, and pauses so another transaction can contend for it.
<3> The second update creates a JDBC round trip after the pause. If Oracle already rolled back the low-priority transaction, the Oracle priority error is reported here and Micronaut rolls the transaction back.
<4> The high-priority checkout uses the same row lock and commits the critical update.

== Run the contention demo

Start the application with `./gradlew run` or `./mvnw mn:run`. Reset the demo account:

[source,bash]
----
curl -X POST http://localhost:8080/demo/reset
----

Start the low-priority transaction. It returns after the row lock is acquired:

[source,bash]
----
curl -X POST 'http://localhost:8080/demo/low?holdSeconds=20'
----

While the low-priority transaction is sleeping, start the high-priority checkout:

[source,bash]
----
curl -X POST http://localhost:8080/demo/high
----

Poll the status endpoint:

[source,bash]
----
curl http://localhost:8080/demo
----

With the settings from `priority-txns.sql`, the expected result is `high=COMMITTED`, `low=ROLLED_BACK`, and an account balance of `100.0`. The event list includes the Oracle error received by the low-priority transaction. Without `PRIORITY_TXNS_MODE=ROLLBACK`, both transactions can commit, because the database has not been instructed to resolve the contention by rolling back the blocker.

In a non-containerized environment, a DBA must apply the same three `ALTER SYSTEM` statements to the Oracle instance. The application user does not need access to `V$TRANSACTION` or `V$SESSION` for this feature.
