common:header.adoc[]

In this guide, you will build a small inventory example with Micronaut Data JDBC and Oracle. A slow stock reconciliation represents background work with `LOW` priority. A customer checkout needs the same last item with `HIGH` priority. When Oracle's priority transaction settings are enabled, Oracle can roll back the reconciliation when the checkout has waited long enough, allowing the checkout to finish.

Micronaut Data applies the priority by setting the Oracle session when the transaction starts and restores the session when the transaction ends. Application code only declares the priority; it does not issue `ALTER SESSION` statements.

== Configure Oracle transaction priority

Transaction priority is an Oracle database feature. The database administrator chooses how long a higher-priority transaction waits and whether Oracle rolls back the lower-priority transaction. See Oracle's https://docs.oracle.com/en/database/oracle/oracle-database/26/admin/managing-transactions.html[Managing Transactions] documentation for the behavior and https://docs.oracle.com/en/database/oracle/oracle-database/26/refrn/PRIORITY_TXNS_MODE.html[`PRIORITY_TXNS_MODE`] parameter reference.

* https://docs.oracle.com/en/database/oracle/oracle-database/26/refrn/PRIORITY_TXNS_HIGH_WAIT_TARGET.html[`PRIORITY_TXNS_HIGH_WAIT_TARGET`] controls how long a `HIGH` transaction waits for a lower-priority blocker.
* https://docs.oracle.com/en/database/oracle/oracle-database/26/refrn/PRIORITY_TXNS_MEDIUM_WAIT_TARGET.html[`PRIORITY_TXNS_MEDIUM_WAIT_TARGET`] controls the equivalent wait for a `MEDIUM` transaction.
* `PRIORITY_TXNS_MODE=ROLLBACK` enables priority-based rollback.

== Inventory operations with different priorities

The service models two business operations. Stock reconciliation is background work, so it uses `LOW` priority. Customer checkout is the critical operation, so it uses `HIGH` priority:

source:InventoryService[]

<1> `@OracleTransactional` is a transaction boundary that also applies the selected Oracle session priority.
<2> Reconciliation obtains the row lock, signals that it is held, and pauses while a slow external count is performed. This gives checkout time to contend for the lock.
<3> This is the reconciliation write and an intentional post-wait JDBC round trip. If Oracle already rolled back reconciliation, the Oracle priority error is reported here and Micronaut rolls the transaction back. No earlier update is needed: `SELECT FOR UPDATE` already acquired the lock.
<4> Checkout uses the same row lock and commits the critical update.

`@OracleTransactional` does not add an automatic retry loop. A priority rollback is a failed transaction, and Micronaut's normal transaction interceptor rolls it back. If an application wants to retry reconciliation, it should start a new transaction, re-read the item, and revalidate that the work is still needed. Blindly replaying stale inventory data could overwrite the successful checkout, so this example leaves that business decision to its caller.

== Inventory HTTP API

Expose the business operations as blocking HTTP endpoints:

source:InventoryController[]

The reconciliation request intentionally remains open while its transaction owns the row lock. Send checkout from a second HTTP request; each request is handled by Micronaut's blocking worker pool, so the application does not need to create or manage an `ExecutorService`.

The controller records operation states and events so the outcome is easy to inspect while running the demo.

== Run the contention demo

Start the application with `./gradlew run` or `./mvnw mn:run`. Reset the demo item:

[source,bash]
----
curl -X POST http://localhost:8080/inventory/reset
----

In one terminal, start the slow stock reconciliation. The request remains open while it owns the row lock:

[source,bash]
----
curl -X POST 'http://localhost:8080/inventory/reconcile?holdSeconds=20'
----

While reconciliation is sleeping, use a second terminal for the customer checkout:

[source,bash]
----
curl -X POST http://localhost:8080/inventory/checkout
----

Poll the status endpoint:

[source,bash]
----
curl http://localhost:8080/inventory
----

With the settings from `priority-txns.sql`, the expected result is `checkout=COMMITTED`, `reconciliation=ROLLED_BACK`, and an item with `availableQuantity=0` and `status=CHECKED_OUT`. The event list includes the Oracle error received by the reconciliation request. Without `PRIORITY_TXNS_MODE=ROLLBACK`, both transactions can commit because the database has not been instructed to resolve the contention by rolling back the blocker.

In a non-containerized environment, a DBA must apply the same three `ALTER SYSTEM` statements to the Oracle instance. The application user does not need access to `V$TRANSACTION` or `V$SESSION` for this feature.
