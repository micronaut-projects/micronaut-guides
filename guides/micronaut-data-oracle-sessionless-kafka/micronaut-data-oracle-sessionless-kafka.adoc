common:header.adoc[]

In this guide you will build a flight-booking workflow with an HTTP controller and two Kafka consumers. The controller reserves a seat in Oracle Database, suspends its transaction, and publishes a payment request. The first consumer processes a simulated payment. The second resumes the original Oracle Database transaction and confirms the booking, or rolls back the reservation if payment is declined.

The controller and consumers exchange the encoded global transaction identifier (GTRID), rather than a JDBC connection. The payment consumer never resumes the transaction and does not need to read the uncommitted booking.

common:requirements.adoc[]

* Docker, for Oracle Database Free and Kafka through Micronaut Test Resources.
* Micronaut Data 5.2.0 or later
* Oracle AI Database 26ai (version 23.6 or later) and a recent Oracle JDBC Thin driver exposing `startTransaction`, `suspendTransactionImmediately`, and `resumeTransaction`.

See the https://docs.oracle.com/en/database/oracle/oracle-database/26/jjdbc/sessionless-transactions.html[Oracle Database sessionless transaction documentation] for database and driver requirements.

common:completesolution.adoc[]

== The Booking Flow

. *Reserve the seat — `BookingController`*
+
Receives `POST /bookings`, reserves the seat, and saves a pending booking. It suspends the Oracle Database transaction, then publishes a `PaymentRequested` message containing the booking ID and GTRID to the `payment-requests` Kafka topic.

. *Process payment — `PaymentConsumer`*
+
Consumes messages from the `payment-requests` Kafka topic and processes payment while the reservation transaction remains suspended. It publishes a `PaymentCompleted` message containing the payment outcome, booking ID, and the same GTRID to the `payment-results` Kafka topic.

. *Complete the booking — `CompletionConsumer`*
+
Consumes messages from the `payment-results` Kafka topic and resumes the original Oracle Database transaction using the GTRID. If payment is approved, it confirms the booking and commits. If payment is declined, it rolls back the reservation.

The sample runs the controller and both consumers in one application. The consumers have separate consumer groups. They can be deployed in separate applications using the same event contracts. Reservation and completion must connect to the same Oracle Database instance and use the same application database user. No connection is held by the application while payment runs, but the suspended transaction continues to hold its database locks.

IMPORTANT: This is an Oracle Database transaction spanning workflow steps. Kafka publishing, Kafka offset commits, and the external payment are separate operations. The example demonstrates propagation and completion; it does not provide atomic delivery or exactly-once booking across these systems.

== Entities and Repositories

source:entity/FlightSeat[]

source:entity/SeatStatus[]

`SeatStatus` represents an available seat, a held reservation, and a completed booking. Micronaut Data stores the enum names in the existing `VARCHAR2` status column. HTTP responses expose the same names through `FlightSeatView`, so the enum has `@Serdeable` while the entity does not.

source:entity/Booking[]

source:entity/BookingStatus[]

`BookingStatus` represents the pending and confirmed states. Micronaut Data stores the enum names in the existing `VARCHAR2` status column, and the HTTP response serializes them as `PENDING` or `CONFIRMED`. The enum is serializable because it appears in `BookingView`; the persistence entity still has no serialization annotation.

source:repository/FlightSeatRepository[]

The derived `findByIdForUpdate` method lets Micronaut Data generate a locking read for the Oracle Database dialect. The service checks the status while holding this lock, changes the mutable entity, and persists it with the standard `update` method. Oracle Database holds the lock until the original transaction commits or rolls back, including while it is suspended. Another reservation for the same seat can wait on that lock. A normal read still sees the previously committed `AVAILABLE` value; it cannot tell you whether a suspended reservation holds the seat.

source:repository/BookingRepository[]

The persistence entities are mutable and have no serialization annotations. The booking ID uses `@GeneratedValue` with its default settings. For Oracle Database, Micronaut Data selects sequence generation and derives the sequence name from the table name plus `_seq`, so Liquibase creates `booking_seq` for the `booking` table. A new booking has no assigned ID; the inherited `save` method inserts it and returns the entity with its generated ID. Sequence values can have gaps after rollback. New bookings use the inherited `save` method; changes to seats and bookings use the inherited `update` method. Both repositories let Micronaut Data generate their SQL.

== Request and Message Contracts

source:dto/BookingRequest[]

source:dto/PaymentRequested[]

source:dto/PaymentCompleted[]

The controller passes only `seatId` to the booking service and uses the payment token from the HTTP request when constructing the payment message. Kafka messages contain only the dedicated `PaymentRequested` and `PaymentCompleted` DTOs. Persistence entities are never sent to Kafka. All events use the database-generated booking ID as their Kafka key. The controller gets this ID from the saved booking before constructing the payment request. The payment request carries the server-selected price because the pending booking is not visible outside its suspended transaction.

Micronaut's propagation API returns the Oracle Database GTRID as a string encoded by `OracleSessionlessTransactionIdCodec`. Include this string in the `transactionId` field of the Kafka messages so the final consumer can resume the transaction. You can customize the codec, but the receiving application must be able to decode the transaction IDs sent by the producing application.

Treat the encoded GTRID as sensitive transaction-control data. Restrict access to these topics, use authenticated encrypted connections outside local development, and avoid logging it. Do not send card details in Kafka messages; the sample uses only demonstration tokens.

== Transactional Booking Service

source:service/PaymentDeclinedException[]

source:service/BookingService[]

<1> Start an Oracle Database sessionless transaction with a five-minute suspension timeout. Oracle Database cancels a transaction that remains suspended past its timeout.
<2> Lock the seat with the generated `findByIdForUpdate` query before checking availability. Change its status to `HELD` and call `update`; create the pending booking with `save`. A competing reservation waits for the lock and then checks the latest committed status, preventing two bookings of the same seat. Failure throws an exception and rolls back the transaction.
<3> `save` returns the booking with its database-generated ID. After the intercepted method returns, Micronaut suspends the transaction instead of committing it. The generated ID and price can be published, but the database writes are still uncommitted.
<4> Resume the transaction whose GTRID is in the active propagation scope.
<5> This read runs inside the resumed transaction and can see the pending booking written by the controller.
<6> A runtime exception rolls back the original transaction, undoing both the seat reservation and the pending booking.
<7> Update the mutable seat and booking through the standard repository `update` methods. A normal return commits both changes together. Micronaut clears the GTRID from the propagation state after completion.

These methods are top-level transaction boundaries on an injected bean. Do not call them inside another active transaction or through self-invocation. The sessionless modes require the default `REQUIRED` propagation and cannot be combined with `@OracleTransactional.Recoverable`.

== Kafka Producer

source:kafka/BookingClient[]

Returning `RecordMetadata` makes each producer method synchronous: it waits for Kafka acknowledgment before returning. The controller waits for its payment request to be acknowledged before returning `202 Accepted`. The payment consumer waits for its result publication before its input offset is committed. There is still a crash window between suspending the Oracle Database transaction and receiving Kafka acknowledgment.

== Controller: Reserve and Suspend

source:dto/BookingView[]

source:dto/FlightSeatView[]

The HTTP response DTOs expose booking and seat snapshots without serializing persistence entities.

source:controller/BookingController[]

<1> Create an empty, lexical Oracle Database propagation scope for the incoming HTTP booking request.
<2> Call the injected transactional service. It saves the booking and returns its generated ID and price on the entity. Its interceptor suspends the Oracle Database transaction before returning to the controller.
<3> Obtain the encoded GTRID after suspension, while the propagation scope is still active.
<4> Publish the payment request after the transaction has suspended. The event carries the GTRID even though the lexical scope has ended.

The controller returns `202 Accepted` with a booking ID after Kafka acknowledges the payment request. Reservation has already run and the Oracle Database transaction is suspended, but payment and booking completion are asynchronous. Blocking Kafka sends and JDBC work run on the blocking executor. The controller is an HTTP entry point; it does not listen to a Kafka topic.

Do not publish the payment request from inside the `SUSPEND` method: a consumer could receive it before Oracle Database has suspended the transaction. A lexical propagation scope is not transported automatically across Kafka or asynchronous threads.

== First Consumer: Process Payment

source:service/DemoPaymentGateway[]

The gateway simulates approval for `demo-approve` and decline for `demo-decline`. Its in-memory map makes repeated payments with the same booking ID return the same result during one process lifetime. Replace this with a payment provider that accepts a durable idempotency key; the demonstration map does not survive restarts.

source:kafka/PaymentConsumer[]

<1> Process payment without entering an Oracle Database transaction or querying the pending booking.
<2> Publish the result with the exact GTRID received in the payment request.

== Second Consumer: Resume and Complete

source:kafka/CompletionConsumer[]

<1> Recognize an already committed confirmation before attempting to resume its completed GTRID. This handles sequential duplicates of a successful result; it is not a complete deduplication mechanism.
<2> Import the encoded GTRID into a fresh propagation scope on the consumer thread.
<3> Resume the original transaction and complete the booking through the injected service.
<4> Catch the expected decline only outside the transactional service, after rollback. Catching it inside that method would allow the reservation to commit.

A declined booking leaves no booking row: the original insert was rolled back. An absent booking can also mean it is pending, expired, or never started. A production workflow needs a separate durable status record to distinguish those outcomes and recognize duplicate declines.

The test submits booking requests through the HTTP API and polls the booking and seat endpoints to verify the outcome.

The approval scenario submits a booking for the seeded `MN123-12A` seat, then polls until the booking is `CONFIRMED` with a payment reference and the seat is `BOOKED`.

<1> Submit a declined booking for the seeded `MN123-12B` seat.
<2> Submit an approved booking for the exact same seat. This request must acquire the lock held by the first reservation, so it can return only after that lock is released.
<3> Poll until the replacement booking is `CONFIRMED` and its seat is `BOOKED`.
<4> Verify the declined booking lookup returns `404`, showing that its pending insert was rolled back.

An absent booking or an `AVAILABLE` seat alone would be a false positive: those are also visible while a reservation is suspended. Successfully booking the same seat again and confirming that the declined booking remains absent verifies rollback through the public API. The tests use a 30-second HTTP request timeout and a 60-second polling deadline, both shorter than the five-minute Oracle Database suspension timeout, so transaction expiry cannot make this scenario pass.

The test has no surrounding transaction and uses a dedicated Micronaut Test Resources scope, with its own Oracle Database and Kafka containers. Liquibase supplies the two demonstration seats. Docker is required; the build stops the disposable Test Resources services after the tests.
