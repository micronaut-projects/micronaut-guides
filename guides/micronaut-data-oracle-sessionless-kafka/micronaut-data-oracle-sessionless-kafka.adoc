common:header.adoc[]

In this guide you will build a flight-booking workflow with an HTTP controller and two Kafka consumers. The controller reserves a seat in Oracle Database, suspends its transaction, and publishes a payment request. The first consumer processes a simulated payment. The second resumes the original Oracle Database transaction and confirms the booking, or rolls back the reservation if payment is declined.

The controller and consumers exchange the encoded global transaction identifier (GTRID), rather than a JDBC connection. The payment consumer never resumes the transaction and does not need to read the uncommitted booking.

common:requirements.adoc[]

* Docker, for Oracle Database Free and Kafka through Micronaut Test Resources.
* Micronaut Data 5.2.0 or later.
* Oracle AI Database 26ai (version 23.6 or later) and a recent Oracle JDBC Thin driver exposing `startTransaction`, `suspendTransactionImmediately`, and `resumeTransaction`.

Read https://docs.oracle.com/en/database/oracle/oracle-database/26/adfns/developing-applications-sessionless-transactions.html[Developing Applications with Sessionless Transactions] in the Oracle AI Database Development Guide for how the feature works, and https://docs.oracle.com/en/database/oracle/oracle-database/26/jjdbc/sessionless-transactions.html[Sessionless Transactions] in the Oracle AI Database JDBC Developer's Guide for database and driver requirements.

== The Booking Flow

The following diagram illustrates the booking flow:

image::oracle-sessionless-kafka-booking-flow.svg[Booking flow: the controller reserves the seat and suspends the Oracle Database transaction, the payment consumer processes the payment, and the completion consumer resumes the transaction to confirm or roll back the booking]

. *Reserve the seat — `BookingController`*
+
Receives `POST /bookings`, reserves the seat, and saves a pending booking. It suspends the Oracle Database transaction, and then publishes a `PaymentRequested` message containing the booking ID and GTRID to the `payment-requests` Kafka topic.

. *Process payment — `PaymentConsumer`*
+
Consumes messages from the `payment-requests` Kafka topic and processes payment while the reservation transaction remains suspended. It publishes a `PaymentCompleted` message containing the payment outcome, booking ID, and the same GTRID to the `payment-results` Kafka topic.

. *Complete the booking — `CompletionConsumer`*
+
Consumes messages from the `payment-results` Kafka topic and resumes the original Oracle Database transaction using the GTRID. If payment is approved, it confirms the booking and commits. If payment is declined, it rolls back the reservation.

The sample runs the controller and both consumers in one application. The consumers have separate consumer groups. They can be deployed in separate applications using the same event contracts. Reservation and completion must connect to the same Oracle Database instance and use the same application database user. No connection is held by the application while payment runs, but the suspended transaction continues to hold its database locks.

IMPORTANT: This is an Oracle Database transaction spanning workflow steps. Kafka publishing, Kafka offset commits, and the external payment are separate operations. The example demonstrates propagation and completion; it does not provide atomic delivery or exactly-once booking across these systems.

The derived `findByIdAndStatusForUpdate` method lets Micronaut Data generate a locking read for the Oracle Database dialect that returns the seat only when it is `AVAILABLE`. The service persists the new status with the standard `update` method while holding this lock. During completion, `findByIdAndStatus` retrieves only a seat whose status is `HELD`. The Java `FlightSeat` and `Booking` entities are records, which Micronaut Data JDBC supports; the Groovy, Kotlin, and Python variants use mutable entities. The Java service creates new record values with the updated status. None of the persistence entities has serialization annotations. The booking ID uses `@GeneratedValue` with its default settings. For Oracle Database, Micronaut Data selects sequence generation and derives the sequence name from the table name plus `_seq`, so Liquibase creates `booking_seq` for the `booking` table. A new booking has no assigned ID; the inherited `save` method inserts it and returns the entity with its generated ID. Sequence values can have gaps after rollback. The controller passes only `seatId` to the booking service and uses the payment token from the HTTP request when constructing the payment message. Kafka messages contain only the dedicated `PaymentRequested` and `PaymentCompleted` DTOs. Persistence entities are never sent to Kafka. All events use the database-generated booking ID as their Kafka key. The controller gets this ID from the saved booking before constructing the payment request. The payment request carries the server-selected price because the pending booking is not visible outside its suspended transaction.

Micronaut's propagation API returns the Oracle Database GTRID as a string encoded by `OracleSessionlessTransactionIdCodec`. Include this string in the `transactionId` field of the Kafka messages so the final consumer can resume the transaction. You can customize the codec, but the receiving application must be able to decode the transaction IDs sent by the producing application.

Treat the encoded GTRID as sensitive transaction-control data. Restrict access to these topics, use authenticated, encrypted connections outside local development, and avoid logging it. Do not send card details in Kafka messages; the sample uses only demonstration tokens.

== Transactional Booking Service

Create an exception to signal a declined payment:

source:service/PaymentDeclinedException[]

Create `BookingService`. It reserves a seat in a suspended transaction and later resumes that transaction to confirm or roll back the booking:

source:service/BookingService[]

<.> Start an Oracle Database sessionless transaction with a five-minute suspension timeout. Oracle Database cancels a transaction that remains suspended past its timeout.
<.> Lock the seat with the generated `findByIdAndStatusForUpdate` query, which returns the seat only when it is `AVAILABLE`. Change its status to `HELD` and call `update`; create the pending booking with `save`. A competing reservation waits for the lock, and Oracle Database then re-evaluates the status condition against the latest committed row, preventing two bookings of the same seat. If no available seat is found, `orElseThrow` throws an exception and rolls back the transaction.
<.> `save` returns the booking with its database-generated ID. After the intercepted method returns, Micronaut suspends the transaction instead of committing it. The generated ID and price can be published, but the database writes are still uncommitted.
<.> Resume the transaction whose GTRID is in the active propagation scope.
<.> This derived finder runs inside the resumed transaction and returns only the pending booking written by the controller.
<.> A runtime exception rolls back the original transaction, undoing both the seat reservation and the pending booking.
<.> Find the seat only when its status is `HELD`; if either derived finder returns no row, the operation fails and the suspended transaction is not committed.
<.> Update the seat and persist the confirmed booking through the standard repository `update` methods. A normal return commits both changes together. Micronaut clears the GTRID from the propagation state after completion.
callout:singleton[]

These methods are top-level transaction boundaries on an injected bean. Do not call them inside another active transaction or through self-invocation. The sessionless modes require the default `REQUIRED` propagation and cannot be combined with `@OracleTransactional.Recoverable`.

== Controller: Reserve and Suspend

Create `BookingController` to reserve seats and to expose bookings and seats over HTTP:

source:controller/BookingController[]

callout:controller[arg0=/bookings]
callout:executes-on[]
callout:post[arg0=book,arg1=/bookings]

<.> Create an empty lexical Oracle Database propagation scope for the incoming HTTP booking request.
<.> Call the injected transactional service. It saves the booking and returns the entity with its generated ID and price. Its interceptor suspends the Oracle Database transaction before returning to the controller.
<.> Obtain the encoded GTRID after suspension, while the propagation scope is still active.
<.> Publish the payment request after the transaction has been suspended. The event carries the GTRID even though the lexical scope has ended.

callout:get[arg0=find,arg1=/bookings/\{id\}]
callout:get[arg0=seat,arg1=/bookings/seats/\{id\}]

callout:serdeable[]

The controller returns `202 Accepted` with a booking ID after Kafka acknowledges the payment request. Reservation has already run and the Oracle Database transaction is suspended, but payment and booking completion are asynchronous. Blocking Kafka sends and JDBC work run on the blocking executor. The controller is an HTTP entry point; it does not listen to a Kafka topic.

Do not publish the payment request from inside the `SUSPEND` method: a consumer could receive it before Oracle Database has suspended the transaction. A lexical propagation scope is not transported automatically across Kafka or asynchronous threads.

source:kafka/CompletionConsumer[]

callout:kafka-listener[]
callout:kafka-topic-listener[]
<3> Recognize an already committed confirmation before attempting to resume its completed GTRID. This handles sequential duplicates of a successful result; it is not a complete deduplication mechanism.
<4> Import the encoded GTRID into a fresh propagation scope on the consumer thread.
<5> Resume the original transaction and complete the booking through the injected service.
<6> Catch the expected decline only outside the transactional service, after rollback. Catching it inside that method would allow the reservation to commit.

A declined booking leaves no booking row: the original insert was rolled back. An absent booking can also mean it is pending, has expired, or was never started. A production workflow needs a separate durable status record to distinguish those outcomes and recognize duplicate declines.

Successfully booking the same seat again and confirming that the declined booking remains absent verify rollback through the public API.
